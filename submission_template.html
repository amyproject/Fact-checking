Fact-checking claims in short videos: can a tuned open model beat frontier models?

Step 1: The task, and why it matters

The job. A trust-and-safety analyst or newsroom fact-checker watches a viral clip, writes down what was claimed, searches for evidence, and files a verdict with sources. Finding and quoting sources is the slow part, and it's the part this system does: transcript → checkable claims → retrieved sources → a label (supported / contradicted / unverified) with a quoted sentence as evidence. The analyst still makes the call.

Short-video fact-checking (this project)
Who does itPlatform trust-and-safety teams, members of the International Fact-Checking Network (IFCN), newsroom verification desks
Why AI hasn't solved itClaims are spoken, so they have to come out of a transcript first. They refer to a specific date and place, often outside the US. And a verdict is only useful with a source the analyst can check, and models invent sources.
Why an open modelThousands of claims a day through a cheap model; transcripts and verdicts stay on infrastructure you control; the weights can be fine-tuned on your own fact-checkers' past work
The dataAVeriTeC (Schlichtkrull et al., NeurIPS 2023): real claims with labels, justifications and the fact-checkers' own research questions

Step 2: A locked test set

65 claims from 38 YouTube clips (28 videos), each labeled by a professional fact-checker. We kept the AVeriTeC claims whose original post was a video, fetched the transcript, and cut long videos into ~90 s windows around each claim so every case looks like a short video. The set was locked before any model ran. The Claims tab shows why each claim was selected and what makes it hard.

Check the labels before trusting the eval. AVeriTeC has four labels and the brief asks for three. Supported → supported, Refuted → contradicted, Not Enough Evidence and Conflicting Evidence/Cherrypicking → unverified. 63 of the 65 test claims come from AVeriTeC's train split, so the fine-tuning data drops them, their videos, their fact-check articles and near-duplicate wordings (step 4).

Step 3: Baselines: open and frontier, off the shelf

Every model gets the same prompts and settings at temperature 0. The off-the-shelf baseline answers from memory and may cite URLs it remembers; the scorer fetches every URL and checks the quote is really on the page. Open models run on Fireworks, frontier models through OpenRouter.

Step 4: The improvement: harness and post-training

We tried the cheap ideas first (prompting and retrieval), then fine-tuning. Each idea started as a guess about why the baseline was failing. The Improvements tab lists all ideas, which ones are built, and the full fine-tuning recipe.

Post-training. A LoRA fine-tune of on examples built from the fact-checkers' own research: their questions, their answers with source URLs, and their justifications. Each example is placed in the exact prompt harness C sends at test time. 10% of the examples have their evidence removed and are labeled "unverified", to teach abstention.

Step 5: Results on the same test set

Step 6: Is the gain real?

Luck moves the score. On 65 claims, a system with a true 50% accuracy scores anywhere from ~38% to ~62% by chance. A gain counts only when it passes two tests, after correcting for running comparisons:

  • McNemar (accuracy metrics) or a paired permutation test (rubric score). These look only at claims where the two systems differ and ask whether the split is lopsided enough to rule out a coin flip.
  • Cluster bootstrap: resample whole videos 5,000 times. The 95% interval for the gap must exclude zero. Claims from one video share a speaker and topic, so resampling single claims would make the interval look tighter than it is.
  • Holm correction: we test planned comparisons at once, so each p-value is adjusted for the chance that at least one passes by luck.

How one answer is scored: 50 checks in 5 areas

Every (claim, system) answer gets the 50 checks below. 20 are deterministic, computed from the answer and the fetched sources. 30 go to a judge model () in one call per answer. The judge is blind: it sees the answer, the evidence and the fact-checker's reference, never the model or system name. A check can be N/A (a numeric check on a claim with no number); N/A checks leave the denominator.

Claim score = Σarea weight × (checks passed ÷ checks applicable in that area), from 0 to 100. Headline metrics stay binary so McNemar applies: source-backed accuracy = A1 (right label) AND B4 (a citation passes every check), with abstentions counting as backed when the fact-checker also found the evidence insufficient.

Trap taxonomy

Each test claim is tagged with the traps that make it hard (rule-based, from the claim text and the fact-checker's metadata; 06_traps.py). Check C4 asks whether the answer noticed its claim's trap. Several checks apply only when a trap is present.

Failure modes

Each answer also gets exactly one failure-mode name, most severe first:

Judge controls

  • Blind: no model or system name in the judge prompt; answers from every system go through the same prompt.
  • Reference-anchored: the judge sees the fact-checker's label, justification and research, so it scores against what the evidence showed, not its own beliefs.
  • Strict: "passes only if a careful editor would agree without caveats"; ambiguous → 0.
  • Self-preference risk: the judge is a frontier model that is also under test. The headline metric (source-backed accuracy) is decided by deterministic checks plus one narrow judge question, so it is largely immune; rubric-score comparisons involving the judge's own model family should be read with that in mind. Swap JUDGE_MODEL to rerun with a different judge.

The improvement ideas

Each idea started as a guess about why the baseline fails. built = in the code and run by run_all.py; data = built and run with no model needed; untested = written, needs a key; planned = not built yet; rejected = considered and dropped, with the reason.

Harness architecture

All harnesses share claim extraction (one call per clip, temperature 0, cached), so differences between systems come from verification alone.
